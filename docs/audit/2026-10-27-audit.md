# Audit 2026-10-27: the-real-snipeit-mcp

## Scope

The whole repository as it runs in production behind a private MCP gateway that runs it from source (stdio, built from source with `npm ci --no-audit --no-fund && npm run build` on Node 24, started with `node --env-file=<repo>/.env <repo>/dist/index.js`), plus the public npm package and release chain. Nine dimensions: input and transport security (`sec-input`), output security and resource limits (`sec-output`), destructive operations (`destructive`), dependencies and MCP SDK (`deps-sdk`), API correctness (`correctness`), tests (`tests`), docs (`docs`), public release chain (`release-public`) and gateway build compatibility (`build-compat`).

- `fce2c98` on branch `modernize/2026-10-27`: `main` (`5f714a9`, v0.1.7) plus a port of the production state by content; `src/` is byte-identical to production. All file:line references below point at `fce2c98` unless they say otherwise; later commits moved lines.
- `5f714a9` (`main`, tag v0.1.7) and the published npm tarballs 0.1.5 to 0.1.7 (registry reads only) for the release and drift findings.
- Not contacted: any Snipe-IT instance, snipeitapp.com, readme.io. Repros used loopback servers and fake fetch implementations.

## Method

One auditor per dimension read the code, ran the tests and wrote repros against the built `dist/` (loopback servers on port 0, fake `fetch`, stdio `tools/list` dumps, a clean container build on a Node 24 `bookworm-slim` image). Every finding then went to an independent verifier (two for majors) who tried to refute it from the evidence. All 84 findings held in the final verdict; for `destructive-02` one of the two verifiers disagreed, which the finding shows. Verifier severities and corrections are listed per finding. Fixes followed the decisions in `docs/design/2026-10-27-modernization.md`; each fix commit carries its tests.

## Dimension summaries

### sec-input

Input/transport security of the client is mostly solid. buildUrl (src/client/snipeitClient.ts:108-131) pins every request to the SNIPEIT_API_BASE origin and path prefix. I tested 18 path variants against dist with a fake fetch: absolute URLs, //host, /\host, tab and CRLF tricks, ../, %2e%2e and backslash traversal are all refused. Query values are encoded with URLSearchParams (CRLF becomes %0D%0A, & and = are escaped). Callers cannot set headers. The bearer token never reaches a different origin: in a loopback redirect test (302/307/308) on Node v26.4.0 and v22.23.1, fetch dropped Authorization on cross-origin redirects, including localhost vs 127.0.0.1.

Two transport defects are reproduced and certain:
(1) The SNIPEIT_TIMEOUT_MS timer is cleared once headers arrive, so a stalled response body hangs the call far beyond the timeout. With timeoutMs=500 the call was still pending after 5 s.
(2) Network errors are retried regardless of idempotency. A non-idempotent POST checkout was executed 3 times by the server.

Also confirmed: two generated maintenance tools send the literal path "/maintenances/:id", so they cannot work.

The remaining findings are minor. Redirects are followed (POST is silently turned into GET on 301/302 and reported as success; the body goes cross-origin on 307/308; the base path pin is bypassed by same-origin redirects). The run has no overall deadline and ignores MCP cancellation. The config accepts http, ftp, file and userinfo bases, and an unset base falls back to a placeholder host. "." and ".." path params are not encoded by the generated tools. Encoded %2f/%5c in raw paths pass through to the server.

No files in the repo were modified. Scratch scripts are in <scratch> (redir.mjs, stall.mjs, reset.mjs, paths.mjs, cfg.mjs).

### sec-output

Output-side security and resource-limit audit of the worktree (HEAD fce2c98). All probes ran against a fake Snipe-IT server on 127.0.0.1 (random port) through a real stdio MCP client (SDK 1.32.2). No vendor was contacted, no repo files were changed, and the scratch dir was removed afterwards. Verdict: logging is clean. Only two logger calls exist; the token goes only in a header and is never logged; the JWT-shaped Snipe-IT token is redacted. The real problems are on the resource side. (1) Tool results have no size cap: `all:true` returns up to 10,000 rows pretty-printed at about 2.6 KB per row. At 5,000 rows the TS SDK client's 10 MiB ReadBuffer overflowed and the connection closed (reproduced). (2) Binary endpoints (backup download, file downloads) get read with res.text() and returned to the model as mangled UTF-8: 3 MiB of zip became 6.2 MiB of text containing 921,599 U+FFFD characters (reproduced). Smaller items: the summary resource fires every per-category request at once and silently returns count -1 under API throttling (reproduced: 93 of 200 categories); one inbound message over 10 MiB ends the server process (reproduced EPIPE); redactSecrets has gaps and error texts bypass it entirely; free-text fields such as notes go to the model verbatim with no data-not-instructions framing and no server-side read-only switch (action1-mcp has both an instruction line and env switches); personal data (email, employee_number) is returned unredacted; the raw_request preview omits `query`. maxToolInputElements exists in SDK 1.32.2 (server/mcp.js:217) but the server does not set it. The zod advisory GHSA-mrhx-c7xc-m3w5 is fixed by zod 4.6.7 (CHANGELOG.md:5). The SDK's 10 MiB limit applies only to INBOUND reads (shared/stdio.js:2,12-14). Outbound send() has no cap, so a server response is never truncated: the receiving client either overflows (TS SDK) or swallows it. Whether the gateway's Python mcp 2.3.0 client has a line limit is unverified.

### destructive

I audited the write paths of the-real-snipeit-mcp-wt at fce2c98. tools/list returns 183 tools, 101 of them marked destructiveHint: 86 generated, 13 hand-written, plus snipeit_bulk_checkout and snipeit_raw_request. Every one of them goes through runGuarded or callWrite and accepts the optional confirm param. No write goes around the guard; raw_request lets only GET through without it. Generated tools match exactly: 86 writes guarded, 59 reads unguarded, and no read tool sends a write method.

The guard is on when SNIPEIT_CONFIRM_WRITES is unset. With it on, a call without confirm returns a preview and sends nothing to the upstream server (checked with a loopback fake: 0 requests).

Weak points I reproduced:
(1) The env flag fails open. "", "on", "enabled", a typo like "ture", or a quoted "\"true\"" all turn the guard off, the empty-string case is pinned by a unit test, and nothing is logged at startup.
(2) The model can confirm a write itself in a single call (delete with confirm:"YES" ran straight away), and the confirm is not tied to any earlier preview.
(3) Non-idempotent POSTs are retried after a connection reset: one confirmed create_hardware reached the server twice.
(4) Cancelling or timing out snipeit_bulk_checkout does not stop the loop. The client got an AbortError after 3 of 5 checkouts, the server finished all 5, and the caller got no partial report.
(5) Previews are not always accurate. The 86 generated tools show a relative URL although the README promises the full one. snipeit_gen_post_auditid leaves out its query params (update_location, location_id, note), which are what the call actually changes. Bulk shows a placeholder URL and a body that differs from what is sent.
(6) The client can only tell a preview from a real result by parsing the JSON text. There is no isError, structuredContent or _meta marker.

Compared with action1-mcp (master switch ACTION1_ALLOW_DESTRUCTIVE defaulting to false, a separate switch for account operations, dry_run defaulting to true, invalid switch values rejected at startup, ACTION1_TOOLSETS=read, audit log events), this server has no master write switch, no read-only mode, no dry_run param and no audit log of executed writes. Bulk partial failures without an abort are reported per item.

A read-only mode must refuse writes at runtime, not unregister them. Removing the 101 write tools would cut tools/list by about 55% and trip the gateway's 20% deploy abort. Any new param, even an optional one, changes the gateway's schema fingerprints.

### deps-sdk

Verdict: deps-sdk is healthy for production. Nothing here is a blocker or major. npm audit --omit=dev and the full npm audit both report 0 vulnerabilities. The runtime tree is @modelcontextprotocol/sdk 1.32.2 (latest v1), zod 4.6.7 and dotenv 16.6.1. npm outdated lists only dev tools plus dotenv (16 -> 18).

zod 3 -> 4 drift: I built main 5f714a9 in a temp copy with its own lockfile (zod 3.25.76, SDK 1.29.0) and compared its tools/list with the current build. Tool names (183), required arrays and defaults are identical for every tool. Resources, templates and prompts are unchanged. So the sibling repo's issue (z.unknown()/z.any() fields becoming required) does not occur here. Three things did change:
- 176 tools lost `additionalProperties:false`.
- Integer fields gained safe-integer minimum/maximum.
- 3 record fields gained `propertyNames`.
All three are loosening or cosmetic, and they are already what production runs.

SDK decision: migrate to v2 (@modelcontextprotocol/server 2.4.0 with serveStdio legacy:'serve'), following the action1-mcp ADR 0001 pattern, in its own change with a tools/list snapshot test. It is a maintenance-horizon recommendation, not urgent. The facts behind it:
- v1 stops at 2025-11-25 (LATEST_PROTOCOL_VERSION). Its README says 2026-07-28 is not planned for v1, and v1 gets fixes only for at least six months after 2026-07-27.
- I prototyped the move in a scratch copy. Swapping three import paths was enough to make tsc clean, and all 119 unit tests pass on Node 26 and 22. Replacing index.ts with serveStdio made a client pinned to 2026-07-28 work, and auto mode then negotiates 2026-07-28 while plain 2025 clients still get 2025-11-25.
- The runtime dependency tree drops from 165 to 8 `npm ls` lines.
- Tool names, required arrays and defaults stay identical. Only `$schema` (draft-07 -> 2020-12) and the `execution` field change, on all 183 tools. That changes the gateway schema fingerprints, so it must be announced.

Node: set engines `>=22.12` (vite 8 / rolldown need ^20.19||>=22.12, vitest 5 ^22.12, eslint 10 ^22.13 on the 22 line). The CI matrix is 20/22 and does not test Node 24, which production runs; use 22/24/26. Do not take TypeScript 7: typescript-eslint 8.72.1 only accepts TypeScript below 6.1.

Smaller items: maxToolInputElements is not set (GHSA-46jr hardening is opt-in), package and serverInfo versions went back to 0.1.5 (npm latest is 0.1.7), and the codegen uses zod-4-deprecated helpers that the vendored spec never reaches.

All temp dirs were deleted and the repo worktree was left untouched.

### correctness

Offline correctness audit of the hand tools, generated tools, resources, prompts and client against vendor/snipe-it-rest-api.json (Snipe-IT 8.2.0). I reproduced the main findings with a loopback mock (127.0.0.1, random port) that drives the real McpServer through the SDK InMemoryTransport. No Snipe-IT instance was contacted. There are three majors. (1) The client retries non-idempotent POSTs on network errors: one tool call reached the server 3 times for snipeit_checkout_accessory, snipeit_bulk_checkout and raw POST /hardware. (2) The codegen does not substitute ':id'-style path params, so snipeit_gen_hardwareidrestore and snipeit_gen_maintenances_copy/_copy_1 send the literal path '/hardware/:id/restore' or '/maintenances/:id' and have no id input. (3) snipeit_create_maintenance sends 'title', but the 8.2.0 spec requires 'name' (and supplier_id); the server's rejection still needs a live check. The minors: checkout/checkin cannot send status_id/name (zod strips unknown keys; spec marks status_id required, needs live check); the generated file-upload tools send JSON instead of multipart; binary downloads are decoded as text; the snipeit://settings resource calls GET /settings, which is not in the spec; the pagination hint assumes a default limit of 50; generated write previews show a relative URL; success messages are dropped when payload is absent; several list filters are not in the spec and some spec filters are missing; and the prompts reference fields and filters that do not exist. Everything else matches the spec: methods, paths, path params and body field names for the hand tools, accessory/component checkin pivot-id semantics, consumable assigned_to, license seat PUT, envelope detection (HTTP 200 status:error is thrown, success payload is unwrapped, 401 'message' is parsed), limit cap 500 and auto-pagination by rows fetched. The only header params in the spec are 'Accept', so dropping header params loses nothing. The spec has no non-string enums, and duplicate operationIds are disambiguated deterministically (snipeit_gen_get_new_endpoint, snipeit_gen_get_new_endpoint_consumables_id_user).

### tests

Overall verdict: the tests are mostly unit tests that check what gets sent. Most tool tests assert method, path, query and body through a mocked client.request, and the core pieces (envelope unwrap/error, SSRF pinning, guard preview, redaction) have outcome assertions. They do not cover the edges that matter for production. Coverage was run in a scratch copy (unit tests only, no token in the environment). Statements: 28% overall. 0% for src/server.ts, src/index.ts and all 145 generated tool files. The SnipeitApiError-to-isError conversion branches (helpers.ts:93-94 and :120-121, plus the catch block in every hand-wrapper) have 0% branch coverage. Two real bugs were reproduced on loopback servers with no test covering them. (1) After a connection reset, a non-idempotent POST is retried: the server received the same POST 3 times. The existing retry test pins this behaviour. (2) fetch follows redirects. A POST became a GET, the tool reported success for a write that never ran, and a same-origin redirect sent the bearer token outside /api/v1. Missing tests: none pins the tool contract (183 tools, names, required params), and none checks that codegen output matches the vendor spec. Codegen is reproducible today: regenerating in a scratch copy gave 145 tools with no diff. An in-memory MCP probe confirmed the write guard holds for all 101 non-read-only tools when confirmWrites=true, but no test keeps it that way. The shared test helper defaults to confirmWrites:false, so every hand-wrapper test runs in the non-default, unguarded mode. tests/integration/live.test.ts does a real POST and DELETE on /categories against whatever instance .env points at. It is gated only on SNIPEIT_API_TOKEN being present (loaded by dotenv) and runs under plain `npm test`. CI runs only test:unit. The repo stayed clean: git status is empty and the scratch dir was deleted.

## Findings

### correctness-1: Non-idempotent POST/PATCH writes are retried on network errors, which duplicates writes

- Severity: major (verifiers: major, major); category `retry-semantics`
- Where: `src/client/retry.ts:66-68`, `src/client/snipeitClient.ts:99`, `tests/unit/retry.test.ts:47-48`
- Status: fixed in 2978269
- Contract impact: None. Internal client behaviour only; tool names, params and defaults are unchanged.

Evidence: src/client/retry.ts:66-68 (any Error whose message matches ECONNRESET|ETIMEDOUT|ENOTFOUND|fetch failed is retriable regardless of opts.idempotent); src/client/snipeitClient.ts:99 computes idempotent=false for POST, but withRetry (retry.ts:89) only uses idempotent for 5xx. Repro: loopback mock that reads the POST body and then destroys the socket. Output: 'snipeit_checkout_accessory -> ERR fetch failed / sent: POST /api/v1/accessories/9/checkout {"assigned_user":3} | POST ... | POST ...' (3x). Same for snipeit_bulk_checkout (POST /hardware/11/checkout 3x) and snipeit_raw_request POST /hardware 3x. tests/unit/retry.test.ts:47-48 asserts the network-error retry without an idempotency check.

Impact: If the connection drops after Snipe-IT processed the write (proxy reset, keep-alive race), the write is replayed up to 2 more times: consumable/accessory checkouts decrement stock repeatedly, assets or users get created twice, and audits are logged several times. For creates with unique keys, the retry fails with 'asset_tag must be unique' and the tool reports an error although the first attempt succeeded, so the LLM may try again.

Recommendation: In isRetriable/withRetry, retry network errors only when opts.idempotent is true (GET/PUT/DELETE). Keep the 429 retry, because Snipe-IT's throttle rejects before processing. Add a unit test: a POST with a socket reset results in exactly 1 request.

Verification corrections:

- Minor precision only. The client's own timeout (AbortError) is wrapped as SnipeitApiError statusCode 0 and is NOT retried (snipeitClient.ts:173-175), so the ETIMEDOUT path covers only socket-level timeouts, not request timeouts. The docstring at snipeitClient.ts:78 claims network errors are retried "once", but the code retries them twice. Recommended fix as in the finding: in isRetriable, return opts.idempotent === true for network errors, keep 429 always retriable, and add a unit test where a POST with a socket reset sends exactly 1 request.
- Narrow the impact statement: timeouts are not replayed (snipeitClient.ts:174-176 wraps AbortError as SnipeitApiError statusCode 0, which isRetriable rejects). Only socket-level failures after the request was sent cause a duplicate write. Also, the docstring at snipeitClient.ts:79 says "network errors once", but the code retries up to 2 more times (3 attempts in total), so that doc comment is wrong as well. The fix should still allow retries for errors that are certain to happen before sending (ENOTFOUND, ECONNREFUSED) on non-idempotent requests, or simply gate all network-error retries on idempotent.

### correctness-2: Codegen ignores ':id'-style path params: 3 generated tools send a literal ':id' and expose no id input

- Severity: major (verifiers: major, major); category `codegen`
- Where: `src/codegen/emit.ts:33-35`, `src/tools/generated/snipeit_gen_hardwareidrestore.ts:15`
- Status: fixed in 2ab966d
- Contract impact: Tool names stay the same (they derive from operationId). The 3 tools gain a new required 'id' param, which changes their schema fingerprint. That is acceptable because the tools are non-functional today, but it has to be stated in the changelog and deploy note. All other generated tools stay byte-identical.

Evidence: Spec paths '/hardware/:id/restore' (POST), '/maintenances/:id' (PUT, PATCH) have no parameters array. src/codegen/emit.ts:33-35 pathTemplate only substitutes '{name}'. Generated src/tools/generated/snipeit_gen_hardwareidrestore.ts:15,21 has inputSchema {...confirmShape} and request path `/hardware/:id/restore`; snipeit_gen_maintenances_copy.ts and _copy_1.ts use `/maintenances/:id`. Repro: call snipeit_gen_hardwareidrestore {id:42} -> sent 'POST /api/v1/hardware/:id/restore' (id silently stripped); snipeit_gen_maintenances_copy {id:7, body:{...}} -> sent 'PUT /api/v1/maintenances/:id'.

Impact: Restoring a soft-deleted asset and updating a maintenance through the generated layer can never work. Snipe-IT gets ':id' as the id and answers not found or error. The tools look valid in tools/list and accept an 'id' that gets silently discarded.

Recommendation: In parseOpenapi/emit, normalise ':name' segments to '{name}'. Synthesise a required path param (integer for 'id') when the spec does not declare it. Also merge path-item-level 'parameters' (not present today, but they are ignored too). Regenerate, and add a codegen test with a ':id' path.

Verification corrections:

- One small correction: the finding says the tools "accept an 'id'". They do not declare one. Zod strips it as an unknown key, so the client gets no error and the id simply disappears, which matches the stated impact. The contract note is right: the tool names stay the same, and the 3 tools gain a required id, so their schema fingerprints change.
- One refinement: the claim that the `id` is silently stripped depends on the MCP SDK dropping unknown keys when it parses `inputSchema`. Either way the handler never uses an id, so the outcome is the same. The contract-impact note is correct. Adding a required `id` changes the schema fingerprints of these 3 tools, and the tool names stay the same.

### correctness-3: snipeit_create_maintenance sends 'title' but the Snipe-IT 8.2.0 spec requires 'name' (and supplier_id)

- Severity: major (verifiers: major, minor); category `spec-mismatch`
- Where: `src/tools/maintenances.ts:44-45`, `tests/unit/maintenances.test.ts:30`
- Status: fixed in edac421
- Contract impact: Sending both keys keeps 'title' as the required input, so tool name, required params and defaults are unchanged. Do not rename the input to 'name' or make supplier_id required in the schema, because either would break the contract.

Evidence: src/tools/maintenances.ts:44-45,52 requires 'title' and states 'supplier_id is optional per spec'. Spec POST /maintenances: required [name, asset_id, supplier_id, asset_maintenance_type, start_date]; no 'title' property; enum asset_maintenance_type ['Maintenance','Repair','PAT Test',...] (description at maintenances.ts:51 and :22 says 'PAT test'). Repro: call snipeit_create_maintenance {asset_id:1, asset_maintenance_type:'Repair', title:'Fix', start_date:'2026-01-01'} -> sent body {"asset_id":1,"asset_maintenance_type":"Repair","title":"Fix","start_date":"2026-01-01"} (no 'name'). tests/unit/maintenances.test.ts:30,40 lock in 'title'.
